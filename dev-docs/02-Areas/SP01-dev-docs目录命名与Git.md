## 1. 四层各放什么

| 目录 | 放 | 不放 |
|------|----|------|
| `01-Projects/` | 按**主题**分的进行中工作：同一功能 / 同一问题的需求、方案、决策、状态 | 长期规范；外部原文；已停用的整夹 |
| `02-Areas/` | **全部项目规格**：技术规范、最佳实践、评价标准、L2/枢纽/L3 清单、叠加原则 | 调查报告；外部摘录；单次主题的需求/方案正文 |

官方 `docs/` 不是上述任何一层的别名。个人写作一律 `dev-docs/`。

## 2. 主题夹（`01-Projects`）

### 2.1 夹名

`R{YYYYMMDD}-{NN}-{主题短名}/`

- 日期 = **首次建夹日**，之后不改夹名日期。
- `NN` = 当日序号，两位。
- **同一功能、同一问题、同一大主题只用一个夹。** 后续增补需求/方案/决策都进这个夹，不要平行再建「差不多的」第二夹。

### 2.2 夹内扁平

**一层文件，不套子文件夹。** 不建 `实施计划/`、`资料/`、`决策/` 之类。只有单夹持续超过约 15 个文件、且两类材料从来不会一起打开时，才允许加一层，并在 `00-README` 写明为什么。

### 2.3 每个主题夹必有的三件套

| 文件 | 职责 |
|------|------|
| `00-README.md` | **索引 + 状态**：文档索引、决策索引、当前阶段、停点、开放问题。文件名固定，保证目录树永远排在最前。 |
| `{YYYYMMDD}-{NN}-需求_{主题}.md` | **该主题全部需求写在这一份**。以后只修订此文，不按轮次再拆 `需求2`。 |
| `{YYYYMMDD}-{NN}-方案_{主题}.md` | **该主题方案写在这一份**。同一功能点的后续方案修订写进本文；只有篇幅或读者明显不同才拆 `{YYYYMMDD}-{NN}-方案_{分题}.md`，仍留在**本夹**。 |

决策要点：写在方案的 `§决策记录`，并在 `00-README` 做**决策索引**（一行一条：决策 / 日期 / 指向）。决策极多时才另建 `{YYYYMMDD}-{NN}-决策_{主题}.md`，仍扁平放本夹。

提问原话：写在需求文的「提问原话」节。不要单独再套一层文件夹。

### 2.4 夹内其它文稿

审查、验收、任务列表：`{YYYYMMDD}-{NN}-{文种}_{标题}.md`，与需求/方案平铺。

**调查报告不进主题夹**，进 `03-Resources/`，主题夹 `00-README` 用相对链接指过去。

## 3. 文件名

### 3.1 技术规范（无日期）

`02-Areas` 里的**技术规范**用规格编号，文件名**不含日期**：

`SP{NN}-{主题名称}.md`

| 规则 | 说明 |
|------|------|
| 编号 | `SP` + 两位数字。按仓内已有技术规范递增，从 `01` 起。编号是规格身份，不是当日序号。 |
| 主题 | 能看懂的短名，不用再加 `技术规范_` 前缀（`SP` 已表示文种）。 |
| 日期 | **不要**写进文件名。首次成文日、修订日写在文内元数据。 |
| 修订 | 改正文不改编号、不改文件名。整份被替代才迁 `04-Archives/`，新规范用下一个空号。 |
| 现行第一份 | 本文件 `SP01-dev-docs目录命名与Git.md` |

禁止再写 `{YYYYMMDD}-{NN}-技术规范_{主题}.md`。

### 3.2 带日期的文稿

日期一律 `YYYYMMDD`。当日**同一目录**序号从 `01` 起、两位。用于需要按时间扫目录的材料。

| 位置 | 模式 | 示例 |
|------|------|------|
| 主题夹 | `R{YYYYMMDD}-{NN}-{主题}/` | `R20260820-01-上游叠加与工作空间围栏/` |
| 夹内需求/方案/其它 | `{YYYYMMDD}-{NN}-{文种}_{标题}.md` | `20260820-01-需求_上游叠加与工作空间围栏.md` |
| 夹内索引 | `00-README.md` | 主题夹内唯一不用日期前缀的文件 |
| 最佳实践 / 评价标准 / 参考 | `{YYYYMMDD}-{NN}-最佳实践_|评价标准_|参考_{主题}.md` | `20260820-03-最佳实践_上游叠加与个性化隔离.md` |
| 调查 / 外部参考 | `{YYYYMMDD}-{NN}-{文种}_{描述性主题}.md` | `20260820-01-调查报告_官方版本_20260813至20260819.md` |

禁止：无日期的 `分析.md`；只靠聊天当档案；为「好看」改带日期文稿的日期前缀（改内容不改创建日，除非整篇迁档）。本条不适用于技术规范的 `SP{NN}` 文件名。

## 4. 调查与外部参考（`03-Resources`）

必须带 **日期 + 序号 + 能看懂的主题**。

- 调查报告：一次取证、对照、走查，区间若有就写进标题（`_{起点}至{终点}`）。
- 外部参考：他仓文档、上游摘录、链接摘要；文首用三行注明来源路径或 URL、取用日、与本仓哪条主题有关。
- 不要覆盖旧调查；新的一天写新文件。
- 现行规格从 Resources 长出来以后，**搬进或写进 `02-Areas`**，Resources 只留来源，不两处各改一版正文。技术规范落地时按 §3.1 取下一个 `SP` 空号。

---

## 5. 归档（`04-Archives`）

主题结束、规格被整份替代、外部参考不再查阅：把**整个主题夹或整篇文件**移入，不拆散、不改文件名。`00-README` 或 Areas 规范里留一句「已迁 Archives」。

## 6. Git（通用约定，不另造体系）

与常见开源习惯对齐，不引入工单号强制、DCO、额外 hook。

**分支**

| 枝 | 用途 |
|----|------|
| `dev-creator` | 个人集成分支。创作者工作从这里拉、合回这里。 |
| `feat/<短主题>` / `fix/<短主题>` | 一条功能或修复。 |
| `feat/R{YYYYMMDD}-{NN}-sync-upstream` | **只做**合上游。 |
| `master` / 官方 PR 枝 | 默认不往上提交，除非你明确要贡献官方。 |

**提交**

- 格式：`type(scope): 为什么`。`type` 取 `feat` | `fix` | `docs` | `chore` | `refactor`。
- 一次提交一件事；`git add` 写显式路径。禁止 `git add -A` / `git add .`。
- 不提交 `.env`、密钥、生成物垃圾。
- 未让你提交就不要 commit；未让你推 `origin` 就不要 push。

## 7. 工作留痕（门闩）

任何问题、需求、方案、决策都要落盘。顺序：

```text
提问原话 → 需求（主题一份）→ 方案（主题一份）→ 决策索引 → 你确认 → 才实施
```

实施 = 改业务代码、嵌工作区规则/技能、建创作者包、`merge` 上游。缺档则停。

## 8. 智能体改写

| 技能习惯 | 本仓 |
|----------|------|
| 写到 `docs/01-Projects` | `dev-docs/01-Projects` |
| 写到 `docs/02-Areas`（技术规范） | `dev-docs/02-Areas/SP{NN}-{主题名称}.md` |
| 写到 `docs/02-Areas`（其它规格） | **最佳实践 / 评价标准 / 参考**才用带日期文件名；需求/方案仍进主题夹 |
| 调查报告写到 Areas 或主题夹 | `dev-docs/03-Resources` |
| 建 `实施计划/` 子目录 | 不建，文件平铺在主题夹 |
| 把本仓 AGENTS 增量写成英文 | **本仓添加的段落用中文**，不英译、不做中英对照；官方原有英文保持英文 |

工作区入口说明见 [dev-docs/README.md](../README.md)。
